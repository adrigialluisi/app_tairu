## Design Context

_Synthesized 2026-09-08 from `CLAUDE.md` + `src/styles/tokens.css` + `docs/tela-*.md` — this project already had a fully specified design system before this file existed, so this is a transcription for the impeccable/polish skills, not new discovery._

### Users
10 real people (the same interviewees from the Mês 1 research round), each testing this prototype on their own phone (iPhone or Android) during a moderated ~35-45min usability session, following a fixed script/scenario read aloud by the moderator. They're mid-task, being watched, on a small screen — not browsing a marketing site. Legibility and native-feeling interaction matter more than visual flourish; anything that reads as "obviously a prototype" or fights their phone's normal conventions costs a data point.

### Brand Personality
Warm, grounded, understated — a travel companion, not a corporate tool or a gamified app. Inherited directly from Tairu's existing shipped app (peach→teal gradient backdrop, deep bordeaux/red accent, cream cards, a circular "sparkle" icon motif) — this prototype reuses that identity rather than reinventing it. Explicitly NOT: flashy, glassy, neon, playful-cartoonish, or corporate-cold.

### Aesthetic Direction
Light theme only (daytime trip-planning use case, matches the existing brand — no dark mode requirement). Native iOS/Android shell conventions throughout: platform-appropriate back affordance, pill vs. Material corner radii, native `<select>`/date pickers kept native (never swapped for custom-built dropdowns — the whole point of the iOS/Android toggle is that it should feel like the OS the participant already uses). Anti-reference: generic "AI slop" — glassmorphism, gradient text, purple/cyan default palettes — none of that fits this brand's warm peach/bordeaux/cream identity anyway.

### Design Principles
1. **WCAG AA is non-negotiable, checked per actual pair used** — not assumed from the starting token values (the original app was explicitly criticized for low-contrast text). See the contrast rules baked into `src/styles/tokens.css`.
2. **Native platform controls stay native.** Don't rebuild what the OS already does well (`<select>`, calendar-adjacent interactions) — restyle the chrome around them, never replace their underlying behavior.
3. **Reuse the established token scale** (`--space-1`…`--space-7`, the color tokens, the two radius scales) rather than inventing one-off pixel values — this keeps every pill/card/input visually related as more screens get built.
4. **Nothing is decorative-only.** State (error, selected, disabled) is never color-alone; icons/borders/text always carry the meaning too, since this also has to work as a real functional prototype, not a mockup.
5. **Every icon-bearing pill (chip, select, badge) needs real breathing room between icon and edge** — establish this once as a token, reuse it everywhere a pill/icon combination shows up in the remaining 10 screens.
